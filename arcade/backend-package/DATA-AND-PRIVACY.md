# Data and privacy

## Today, in demo mode

The DGD App 2.0 arcade sends nothing. Its progress is stored on the phone, and **Settings → Erase progress on this device** clears it.

## Once the server is live

### What the server stores

| Table | Contents |
|---|---|
| `players` | Random player id; SHA-256 of the token; `created_at` and `last_seen`; `device_hint` (the platform name); assigned handle and its reroll count; XP total; status (`ok`, `xp_only` or `banned`); legacy Tablet Run and Ledger counters |
| `mini_rounds` | One row per round: game, UTC day, stars, level or eras, score, XP paid, the When Pigs Fly loadout, and the open and claim times |
| `xp_events` | The dated XP ledger that the weekly board reads |
| `badges` | Badge and the time it was earned |
| `passage_profile`, `passage_abilities` | When Pigs Fly lifetime points, spendable points, and ability levels |
| `expeditions`, `tablets`, `tablet_state`, `ledger_plays` | Tablet Run and Daily Ledger. DGD App 2.0 never writes these. |

### What the server does not store

- **No IP addresses.** The rate limiter keys on the client address, or a token hash, held in process memory only. Nothing about addresses is written to disk, and a restart clears it.
- **No names, emails, phone numbers, contacts or location.**
- **No advertising ID** and no device identifier from the OS. The player id is generated by the server.
- **No analytics, crash reporting or third-party SDKs** in the app or on the server.

The server's own log lines carry errors only. The proxy's access log is yours to configure. If it records IPs, that is data collected, and it belongs in the retention decision below.

## Deletion

The app offers deletion from Settings. It calls `DELETE /v1/me`, which works as follows:

- It removes the player's rows from every table in one transaction. `tablets` goes first, through its `expeditions` join, so nothing is left orphaned.
- The token stops working immediately.
- It returns the per-table row counts, which can serve as a receipt.

Both stores ask whether users can request deletion, and with this route the answer can be yes, inside the app.

## Retention: a decision for you and DGD

**Nothing expires today.** We propose:

- **Inactive players** (`last_seen` older than 12 months) are deleted by the same code path as `DELETE /v1/me`.
- **`mini_rounds` and `xp_events` older than 90 days** are trimmed to the totals already held in `players` and `passage_profile`. The weekly board only reads the current week, and the tuning report defaults to recent runs.
- **Backups** are kept for 30 days.

Once you agree a rule, we will add a script for it, with tests, to the server repo.

## Changes DGD has to approve before a live build ships

- **The privacy policy** (`arcade/PRIVACY-DRAFT.md`). It needs a section for the arcade server, giving:
  - what is stored, as listed above;
  - why: progress, standings and abuse limits;
  - where the server is hosted;
  - the retention period;
  - deletion from Settings.
- **Play Data safety.** It currently declares no data collected. A live build sends app activity (game results) and an app-generated identifier to a first-party server. Both are encrypted in transit, and both can be deleted from inside the app.
- **The Settings wording.** With a server, the arcade's Settings shows the anonymous play record, its leaderboard name, and **Delete my play record**. That text is the designer's, and it must be checked against the Data safety answers. This is review item R12 from the DGD 2.0 audit.
