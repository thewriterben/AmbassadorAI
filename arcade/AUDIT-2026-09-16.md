# DGD Arcade — pre-demo audit, 2026-09-16

> **Fix pass, same day.** B1-B7 and C1-C8 are closed; 16 server tests (up from
> 13) and 27 Flutter tests pass. What changed, and what deliberately did not:
>
> - **B1 finish race** — the body is now read before any check, and the
>   expedition is claimed with a conditional `UPDATE … WHERE finished_at IS
>   NULL`. A single SQLite statement is the whole check-and-set, so one of any
>   number of concurrent finishes wins and the rest get the idempotent replay.
>   New test fires 25 at once and asserts exactly one payout and at most one
>   `xp_events` row.
> - **B2 mini-game XP** — rounds are now server-issued: `POST /v1/mini/:game/start`
>   returns a signed single-use token, and the claim checks the signature, the
>   owner, single use, and a per-game duration floor. Bare `curl` now gets
>   `round_token_required`.
>   **This does not verify the reported score.** The content lives in the client,
>   so the server cannot mark the answers; it can only refuse rounds it never
>   issued. Closing that properly means moving mini-game content server-side the
>   way the question bank already is. Until then the weekly board measures "played
>   a lot", not "played well", and the daily cap is what bounds it. Said plainly
>   in the code and in the build doc.
> - **B3 rate limiting** — keys on the bearer token, then a trusted-proxy hop
>   (only when `ARCADE_TRUST_PROXY=1`), then the socket address. No shared
>   `'anon'` bucket, and eviction now drops only expired entries.
> - **B4** — the dev-secret check no longer depends on `NODE_ENV`; it refuses
>   everywhere unless `ARCADE_ALLOW_DEV_SECRET=1` is set explicitly.
> - **B5** Fisher-Yates. **B6** a `uint()` guard on every client number.
>   **B7** signature compare is byte-length safe.
> - **C1 ingot double-gravity** — the two gravity passes are merged into one
>   `(from, to)` per gem, so no gem gets two summing move effects.
> - **C2-C8** — win sting fired once, `celebrate()` guarded on `mounted`, seal
>   goal text counts layers, `VALUE` → `SCORE`, demo makes no network calls,
>   `Progress.load()` parses defensively, Chain Builder's finish is guarded.
>
> **Second fix pass.** C10, C11 and F2-F8 are now closed too. 28 Flutter tests
> (up from 27), 16 server tests, analyzer clean.
>
> - **F2 hard casts** — `api.dart` gained `field()`, `intField()` and
>   `stringsField()`, which raise `ApiException` instead of `TypeError`. Every
>   screen already handles `ApiException`; a bare `as` cast broke that contract
>   silently. `TabletQuestion`/`TabletVerdict` and the finish and leaderboard
>   parsers all use them now. `_onTablet` additionally resumes the run from a
>   `finally`, so no escape from that block can leave the game paused forever.
> - **F4 `init()` race** — memoises the in-flight *Future*, not the token, so
>   concurrent callers share one registration instead of creating two players.
> - **F5** Chain Builder's finish is guarded. **F6** `setState` after dispose
>   fixed in the ledger, Rope and Blocks. **F3/F8** "earned" → "was awarded",
>   "rewarded rounds" → "XP-eligible rounds". **F7** `payout.wav` and its dead
>   accessor are gone.
> - **C10** `ScrollController` disposed; `Progress.load()` failures now surface
>   via `onError` instead of vanishing.
> - **C11** `Board.deadlocked` is set when shuffling cannot find a legal move,
>   and the session ends the level instead of soft-locking it.
> - New test: no gem appears twice in one step's `falls` (the C1 invariant),
>   across 40 seeds × 40 moves on ingot boards.
> - **C9 fixed, later the same day.** `GemComponent` now tracks the completers
>   it hands out and completes them in `onRemove`, so the cascade loop unwinds
>   instead of staying suspended forever on an effect that will never finish;
>   `Match3Game._dead` then stops the unwound loop animating, playing audio or
>   calling `onEnd` into a route that has gone. Four tests in
>   `test/teardown_test.dart` cover the contract.
>
> **Still open:** B8 (bank id stability — only bites if an existing question is
> edited) and **F1, the signup CTA, which needs legal review rather than a code
> change**.

Three parallel reviews (Flutter client, backend security, demo build and content
compliance) plus the project's own bank and compliance linters. The backend
findings were reproduced against a running server, not inferred.

Ordered by what blocks what, not by severity alone.

## Blocks hosting the backend — must fix before it is exposed

### B1. CRITICAL — `finish` is a TOCTOU race: 100× XP from one honest run
`server/src/app.ts:186-219`

The `await c.req.json()` sits *between* the "already finished?" guard and the
write. Concurrent requests all pass the guard, then all award XP.

Reproduced: one legitimate 3/3 expedition worth 160 XP + 100 concurrent
`POST /finish` with bodies held back one turn → **16,000 XP, 100 completions,
one rewarded expedition consumed**. The daily cap is entirely defeated.

Fix: move the body read above `getExp`, or wrap guard-and-write in
`BEGIN IMMEDIATE`/`COMMIT`. There are currently **no transactions anywhere in
`src/`**. Every other handler is safe because its `await` happens *before* the
read-check-write; each was verified under the same attack.

### B2. CRITICAL — mini-game XP is entirely client-submitted
`server/src/app.ts:291-335`

There is no server-side game state for mini-games. `right`, `total` and `extra`
come straight from the request body into the XP formula — no token, no nonce, no
issued round, no proof of play. `curl` alone yields **4,350 XP/day** across the
four games, against a legitimate daily maximum of roughly 370.

This matters beyond the number: **Coin Quest reports through this same path**
(`app.ts` game `coin_quest`, called from `match3_screen.dart:71`), so the
unverifiable route is the dominant source of XP on the weekly board. The claim
recorded in `DGD-Arcade-Build.md` — that the client never submits a score — is
false for most obtainable XP. The build doc has been corrected.

Fix: issue a signed round token the way tablets do, or accept that the
leaderboard is advisory and say so in the UI.

### B3. HIGH — rate-limit key is attacker-chosen, and `'anon'` is a global bucket
`server/src/auth.ts:68`

`X-Forwarded-For` is read raw with no trusted-proxy validation and no fallback to
the socket address. 400 unauthenticated `POST /v1/players` with fresh spoofed
XFF → **400 players created, 0 rate-limited.**

Worse in the other direction: with no auth header and no XFF the key is the
literal string `'anon'` — one bucket shared by all anonymous traffic. One host
burning 118 requests makes **a different client's first-ever signup return 429**.
Global signup denial from a single machine, no spoofing needed.

Also: `hits` is in-memory (do not scale horizontally), the window is fixed so a
2× burst at the boundary is free, and `auth.ts:73`'s `hits.clear()` at 50k keys
lets an attacker flush every legitimate counter.

### B4. MEDIUM — the production guard keys on the variable most likely to be missing
`server/src/config.ts:78`

`assertProductionConfig` no-ops unless `NODE_ENV === 'production'`. The Dockerfile
sets it; a systemd unit, a bare `npm start` or a PaaS that doesn't inject it will
not — and then the server boots on the dev secret that is committed to this repo.
Gate on "the secret is the dev default", regardless of environment.

### B5. MEDIUM — option shuffle is badly biased
`server/src/app.ts:117` — `sort(() => Math.random() - 0.5)` is not a shuffle.
Measured over 400k trials at the bank's real shape: option 0 lands correct
**35.95%** of the time, not 25%. A bot that waits out `minLatencyMs` and always
picks the first option clears a 3/3 expedition 4.6% of the time instead of 1.6%.
Use the Fisher-Yates already present at `scheduler.ts:15`.

### B6. MEDIUM/LOW — unvalidated JSON reaches SQLite as live 500s
`{"right":{}}` → `app.ts:296`; `{"stumbles":true}` → `app.ts:212` (and
`finished_at` is then never written); `?limit=abc` → `progress.ts:74`. Validate
with `Number.isFinite` before binding.

### B7. LOW — `verifyTablet` throws on a multibyte signature
`server/src/auth.ts:43` compares string length, `timingSafeEqual` compares bytes.
43 multibyte characters passes the guard and throws `RangeError`. Contained by
Hono, but a verifier that throws on attacker input is the wrong shape.

### B8. LOW — editing an existing bank question breaks in-flight tablets
`bank.ts:44` derives the id from `sha1(section + prompt)`. Fixing a typo changes
the id and `bank.get(t.question_id)!` throws forever for stored rows. Adding
files is safe; editing existing ones is not. Relevant while the bank grows
170 → 300.

### Verified sound under direct attack
No SQL injection (every value-carrying query uses bound parameters; the only
interpolation is hardcoded migration names). No IDOR — no endpoint accepts a
player id from the client. Tokens are 192-bit random, stored only as SHA-256,
returned once. Tablet single-use holds under concurrency (6 concurrent answers →
`200, 409, 409, 409, 409, 409`); nonce, expiry and ordering are all genuinely
enforced. Questions never ship to the client. The ledger is fully server-side and
not racy. `rewardedRoundsPerDay` is not racy. Client-reported `runMs`/`stumbles`
are stored but never trusted in any calculation. `awardXp` is a real single
chokepoint.

Structural note: the tablet HMAC is close to decorative — the nonce travels in
cleartext inside the token, so the signature grants nothing the `tablets.nonce` +
`answered_at` columns don't already enforce. The database is the real enforcement
point. Worth knowing before a future refactor "simplifies" by trusting the token.

## Ships in the Coin Quest demo — fix before it goes out

### C1. HIGH — ingot delivery draws a whole column in the wrong place
`match3/model/board.dart:613,625`, consumed at `match3_game.dart:427`

`_resolveStep` calls `_applyGravity(falls)` twice, appending to the same list.
Gems that fall in both passes appear **twice** in `step.falls` with different
`(from,to)` pairs, so the view attaches two concurrent `MoveToEffect`s to one
component. Flame's effect is delta-based, so they sum and the coin overshoots
downward by the first distance — often off-board, where it is clipped away.

Visible on every ingot level (31-40, 43, 46, 47, 50, 53-55, 57, 58, 60): the top
of that column looks empty while taps there still register. `comp.pos` stays
correct, so it self-heals on the gem's next move — possibly not before the level
ends. Does not hang the board.

### C2. MEDIUM — the win sting plays twice and truncates itself
`match3_screen.dart:66` fires `Audio.win()`, then `match3_game.dart:936`
fires it again 450 ms later. Same memoised player, `minGapMs: 0`, so the second
call restarts the sample and cuts the first off. Every win.

### C3. MEDIUM — the celebration runs after the player has left
`match3_screen.dart:73` — `await game.celebrate()` has no `mounted` check before
it. Back out during the end delay and five seconds of win audio, fireworks and
the spoken line play over the level map.

### C4. MEDIUM — goal text and counter disagree on two-layer seal levels
`levels.dart:90` counts cells, `session.dart:71` counts cells × layers. Levels
17, 20, 45, 52, 59 read "STRIP 8 LEDGER SEALS" beside a counter showing `0/16`.

### C5. MEDIUM — the demo still calls localhost
`main.dart:31` runs `ArcadeProgress.instance.load()` unconditionally, which
registers an anonymous player against `http://localhost:8787` on every cold
start, and `match3_screen.dart:71` posts a mini-round on every level win. Both
fail silently and invisibly, but a no-backend build should make no doomed
requests. Wrap both in `if (!Dev.demoBuild)`.

### C6. MEDIUM — the score is labelled "VALUE"
`levels.dart:88,98`, `match3_screen.dart:158`

The most prominent number on screen, rising as you play, is labelled **VALUE** —
in an app branded for a real gold-backed asset, directly under a disclaimer
reading "XP and badges have no monetary value". This is the only compliance
finding that ships in the demo. Rename to SCORE / "Reach N points".

### C7. MEDIUM — blockers animate when dragged
`match3_game.dart:257` — `onDragStart` has no blocker check (the tap path at
`:242` does), so dragging a vault or ingot slides it out of its cell and snaps it
back. Reads as a bug against "obstacles are scenery".

### C8. LOW — `Progress.load()` can silently downgrade saved progress
`match3/progress.dart:28` — `int.parse` without `tryParse` over *every* key in
the shared store, and `getInt(k)!`. No key collides today, so this is latent. But
`load()` clears the maps *before* the loop, so a throw leaves them empty while
the store is intact — the map then shows level 1 only, and a replay overwrites a
stored 3-star via `record()`'s `stars > (_stars[level] ?? 0)`. Called unawaited
with no `catchError`, so nothing would surface it.

### C9. LOW — leaving mid-cascade strands the board in memory
`match3_game.dart:1018` — `moveTo`/`pop` complete only from the effect callback.
When the widget is disposed the game stops updating, the effects never finish,
and the suspended continuation keeps the whole `Match3Game` and component tree
alive. One stranded board per mid-animation exit — genuinely unbounded over a
long session.

### C10. LOW — missing `dispose()` on five States
`level_map.dart:22` (`ScrollController`, also a lint finding), plus the
`ValueNotifier`s in `match3_screen.dart`, `tablet_run_screen.dart`,
`daily_ledger_screen.dart`, `chain_builder_screen.dart`. A new `Match3Game` is
created on every retry with the old one never released.

### C11. LOW — `shuffle()` can leave an unwinnable, unloseable board
`board.dart:229` — both the `movable.length < 3` early return and the 100-attempt
loop fall through leaving the last arrangement. If it has no legal move, `swap()`
always returns invalid, `movesLeft` never decrements and the state never leaves
`playing`. Probability is negligible on a 9×9; there is no fallback at all.

## Full build only (not in the demo)

### F1. MEDIUM-HIGH — a signup CTA for a financial asset, inside the game
`arcade/run/tablet_run_screen.dart:367` — a button reading "Ready to validate?
Create your account at digitalgold.co", launching that URL from the results
sheet immediately after an XP award.

Whatever the wording, an educational-only game funnelling players to account
creation on a gold-backed-asset platform has the shape of a financial promotion.
**This needs legal review before it ships, not a copy edit.** It is the
highest-risk item in `lib/`.

### F2. MEDIUM — hard casts on server JSON dead-end three screens
`tablet_run_screen.dart:66` and `:98`, `mini_shell.dart`. Response bodies are
destructured with unchecked casts inside `try { } on ApiException`. A `TypeError`
escapes that clause. At `:66` the game has already set `_paused = true` and
nothing clears it — **the run freezes permanently**, invisibly, because the
future is dropped. Live risk while the backend is still being stood up.

### F3. MEDIUM — "earn" in user-visible copy
`tablet_run_screen.dart:311` — "…so it earned no XP." Banned vocabulary.
Use "so no XP was awarded."

### F4. MEDIUM — `ArcadeApi.init()` has no in-flight guard
`api.dart:34` — `main()` fires `load()` unawaited; tapping a server-backed screen
during that round-trip runs `init()` again with `_token` still null, posting a
second `/v1/players`. The second response overwrites the stored token, orphaning
XP already credited to the first player and leaving a ghost row on the board.
`Audio._playerFor` memoises its *Future* for exactly this reason; `init()` should
too.

### F5. MEDIUM — Chain Builder's check button is re-entrant
`chain_builder_screen.dart:41` — double-tap inside the 700 ms advance delay
double-counts `solved` ("4 of 3 right" to the server), skips a chain, and on the
last one stacks two results sheets.

### F6. MEDIUM — `setState` after dispose
`daily_ledger_screen.dart:38,41,76,80,81` (the `finally` checks `mounted`, the
statements that need it do not), `rope_game.dart:79`, `blocks_game.dart:55`.

### F7. LOW — `payout.wav` ships with zero call sites
`audio.dart:41,244`. Dead code, but the filename "payout" would appear in an APK
teardown. Delete both.

### F8. LOW — "rewarded rounds" reads as an entitlement
`mini_shell.dart:166`, `tablet_run_screen.dart:315`. Not on the banned list but
adjacent. "XP-eligible" is safer.

  "investment" at L49, "retire" at L74) — documentation, not player-facing
