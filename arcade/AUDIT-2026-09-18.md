# DGD Arcade — red-team pass, 2026-09-18

> **Scope and authorisation.** Benji's own client and server, attacked locally.
> The server ran from this tree against a throwaway SQLite file; the Android
> work ran on a fresh API 35 emulator with a reverse tunnel to that server.
> Nothing here touched digitalgold.co, the DGD App, or any hosted service. No
> fixes were applied beyond the one test fixture below; every finding is a
> regression test or a recorded reproduction, and fixing is a separate change.
>
> **Baseline first.** `npm test` in `server/` had been failing at import since
> the bank was split into `data/bank/*.md`: the suite still loaded the retired
> seed file, so the "16 passing" in the 16 Sept header could not be checked.
> One-line fixture fix; 16 of 16 pass. That is the baseline. New today:
> `server/test/redteam.test.ts` (12 cases: 6 hold or are accepted, **6 open
> findings under `todo`**, so the suite exits green and flips visibly when a
> fix lands) and `app/test/arcade_api_test.dart` (5 cases, the first tests of
> the network and identity layer). **28 server tests, 33 Flutter tests, exit 0.**
>
> **Environment.** No Android device or AVD existed, so one was created
> (`dgd_api35`, Google APIs image, so `adb root` works). No Mac here: the iOS
> section is a static review plus a checklist for whoever has the Mac. The
> whole `arcade/` tree, server included, was untracked in git; it is now on the
> `arcade-redteam` branch with an as-found snapshot as the first commit.
>
> **What changed since 16 Sept, in one line each.** The demo build phones
> home on cold start (A1, C5 was not closed). The mini-game daily cap does not
> survive UTC midnight (R1, new, HIGH). A tablet can be answered after its
> expedition is finished (R6, new). B8 reproduced and still 500s (R7). The
> distributed DEV APK mints real XP, bounded only by the 15 s floor and the
> daily cap (A4). The kill switch in the Integration Brief is not implemented
> (A8). B2, F1 and the ALLOWLIST sign-off are carried forward unchanged.

## Server — `server/src/`

### R1. HIGH — the mini-game daily cap does not survive UTC midnight (new)
`app.ts:357-362` vs `app.ts:403-409` · `OPEN R1` in `redteam.test.ts`

`mini_rounds.day` is stamped when a round is **opened**; the cap counts claimed
rounds whose `day` equals the **claim** day. Rounds opened before midnight and
claimed after it are counted against a day that contains none of them, so the
count is 0 for every claim and all of them pay. The 60-minute token life bounds
the window, not the quantity: with the 120/min limiter that is hundreds of
pre-opened rounds claimable in the hour after midnight, per game.

Reproduced with the suite's clock control: 15 rounds opened 60 s before
midnight, claimed 2 min later → **15 of 15 paid; the cap is 10.**

This corrects `DGD-Arcade-Build.md`, which says the cap "is what bounds"
mini-game XP. It bounds it inside a UTC day only.

Fix shape: count by the round's own `day`, or stamp `day` at claim, and pick
one for the whole file.

### R3. MEDIUM — anonymous signup has no cap beyond the generic limiter
`app.ts:58`, `auth.ts:133` · `OPEN R3`

`POST /v1/players` is unauthenticated and has no cap of its own: no device
binding, no attestation, no proof-of-work. Live against the running process,
**150 concurrent registrations from one address: 120 succeeded, 30 got 429** —
exactly the per-minute limit and nothing else. Each identity can climb the
weekly board. The client compounds this: any JSON 401 makes it forget its token
and register a fresh player on the next call (`api.dart:141-145`, covered by
the Flutter test "a 401 from any endpoint drops the identity").

### R4. MEDIUM — the fixed-window limiter admits a double burst at the boundary
`auth.ts:137-152` · `OPEN R4` · residual of audit B3, unchanged

The counter resets on the first hit more than 60 s after the window opened, so
`perMinute` at t=0 and `perMinute` at t=61 s both pass: **240 requests in 61 s
from one address.** Also still true: the map is per-process (do not scale
horizontally as-is), and unauthenticated traffic with no socket information
shares one `u:unattributable` bucket.

### R6. LOW-MEDIUM — a tablet can be answered after its expedition is finished (new)
`app.ts:177-218` · `OPEN R6`

The issue path checks `finished_at` (`app.ts:136`); the answer path does not.
A tablet left open survives `finish`, and answering it afterwards returns 200,
writes the tablet row and updates spaced-retrieval mastery through `record()`.
XP is unaffected because `finish` has already paid, so this is a state-machine
gap rather than an XP hole. Reproduced: **200 instead of 409.**

### R7. LOW — B8 is still open: a vanished bank id is a 500, forever
`app.ts:150, 189`, `bank.ts:44` · `OPEN R7`

A question's id is `sha1(section + prompt)`, so editing a prompt gives it a new
id and every tablet row referencing the old one hits `bank.get(...)!` and
throws. Reproduced without file I/O by removing the id from a private bank
instance: **issuing the tablet returns 500.** The bank is growing 170 → 300;
this will happen.

### R9. LOW — a corrupt server-written JSON column is a 500
`app.ts:190, 274, 304` · `OPEN R9`

`JSON.parse` on `tablets.option_order` and `ledger_plays.guesses` is
unguarded. Only reachable through a damaged database, but a reader that throws
on its own stored data is the wrong shape. Reproduced: **500.**

### R2. ACCEPTED — a mini-game score is whatever the client says
`app.ts:346-349, 400-426` · `ACCEPTED R2` · residual of audit B2, on the record in the code

The server clamps (`right ≤ maxRight`, `XP ≤ 200`, rounds ≤ 10/game/day) but
cannot mark answers whose keys ship in `lib/arcade/knowledge/content.dart`.
The honest ceiling per UTC day, now pinned by a test so it cannot widen
silently: pillar_sort 1,600 · design_or_myth 1,200 · coin_quest 800 ·
chain_builder 750 → **4,350 XP/day per identity**, and R3 supplies
identities. Live: one scripted player banked 1,600 XP in about 90 s of wall
clock, all "legitimate". Until the content moves server-side, the weekly board
measures "played a lot", as the code says. Combine with R1 and the ceiling is
gone.

### R8. INFORMATIONAL — `status = 'xp_only'` means zero XP, and nothing ever sets it
`db.ts:24`, `app.ts:110, 315, 412`, `progress.ts:68` · `ACCEPTED R8`

Every award path gates on `status === 'ok'`; only `banned` is refused or
dropped from the board. So the middle rung of the abuse ladder is a manual SQL
update whose name reads as the opposite of what it does, and the plausibility
flags stored per expedition never escalate anyone. Documented, with a test
that greps the source to confirm nothing writes it.

### R12. INFORMATIONAL — CORS is `*` unless `ARCADE_CORS` is set
`config.ts:14, 114`, `app.ts:52` · `ACCEPTED R12`

Only fatal under `NODE_ENV=production`. Low severity: bearer auth, no
credentials mode, so a foreign page cannot ride a session. It can call the
registration endpoint, which is R3's problem, not this one.

### Verified sound under direct attack
- `HOLDS R5` — a fresh spoofed `X-Forwarded-For` per request does not buy a
  fresh bucket when no proxy is trusted; when one is, only the last hop keys
  the bucket and a different last hop is a different client.
- `HOLDS R10` — the board carries exactly `{handle, rank, xp, you}`; no `p_`
  ids, no tokens; rerolls stop at the daily cap with 429.
- `HOLDS R11` — `/healthz` is the only unauthenticated read and returns only
  `{ok, bank, day}`; every `/v1/*` route is 401 without a token. Note it sits
  outside the limiter.
- Live soak against the real process: claim before the 25 s floor → `too_fast`;
  13 same-day rounds → 10 paid, 3 zero; 25 concurrent replays of one claimed
  round → 25 × 409; the 16 Sept finish-race test still passes.
- Static, unchanged: no SQL string concatenation with user data; every
  untrusted body goes through `uint()`/`intOrNull()`; still **no transactions**
  anywhere (atomicity rests on single conditional `UPDATE`s, which R1 shows
  is not the same as a consistent day count); the container runs as root.

## Android — static review and emulator run

Emulator: `dgd_api35` (Android 15, Google APIs x86_64), `adb reverse
tcp:8787`, so the APKs' compiled-in `http://localhost:8787` reached the local
server exactly as a USB phone would.

### A1. HIGH — the demo build registers a player on cold start; C5 was not closed
`app/lib/main.dart:33`, `app/lib/arcade/progress.dart:41-63, 101`

`main()` calls `ArcadeProgress.instance.load()` unconditionally. `load()` →
`refresh()` → `ArcadeApi.init()` → `POST /v1/players`. The only demo gate is
on `startMini`, so the 16 Sept fix closed the level-win call and left the
cold-start one.

Reproduced: fresh scratch DB, `dist/DGD-Arcade-demo.apk` (built by
`sideloadbuild.cmd` with `DGD_DEMO=true` — the screen confirms it: no
standings card, "More games coming soon"), 20 s after launch → **one player
row, `device_hint = android`**, a TIME_WAIT socket to :8787, and
`FlutterSharedPreferences.xml` on the device holding `flutter.api.token`,
`flutter.api.player` and a full `ar.snapshot`.

On a real phone today the default URL is unreachable, the attempt fails as
"offline" and nobody sees it — which is why it was missed. Any demo build that
carries `ARCADE_API` registers every installer with the backend: an identity,
a device hint and an IP, from a build described as "no backend" under a store
draft that says "no data collection". This is the compliance finding of the
pass. Fix shape: gate `load()`/`refresh()` on `Dev.demoBuild` the way
`startMini` already is, and add a test that a demo build makes zero requests.

### A2. MEDIUM — `allowBackup` defaults on, and the bearer token is plaintext
`app/android/app/src/main/AndroidManifest.xml:3-7`

Confirmed live: `dumpsys package` shows `ALLOW_BACKUP`, and the token sits in
`shared_prefs/FlutterSharedPreferences.xml`. The identity therefore travels in
Auto Backup and any device-to-device transfer. Same class as iOS I2. Fix
shape: `android:allowBackup="false"` or a backup rules file that excludes the
prefs, and consider the platform keystore for the token.

### A3. MEDIUM — a release build silently debug-signs, and nothing is minified
`app/android/app/build.gradle.kts:55-67`

Without `key.properties`, `flutter build apk --release` produces a
debug-signed "release" with only a `println` to say so — every APK in `dist/`
is one. No `minifyEnabled`, no `shrinkResources`, no ProGuard rules; endpoint
strings and Kotlin symbols are as-written. Dart is AOT but `DART_OBFUSCATION`
is off. A Play upload will be rejected, which is the good outcome; the risk is
a debug-signed sideload circulating as "release".

### A4. MEDIUM — `dist/DGD-Arcade-DEV.apk` is a distributable that mints XP
`app/lib/dev.dart:15`, `app/lib/match3/ui/match3_screen.dart:54-67, 80-81`

The DEV menu is compile-gated (`const bool.fromEnvironment('DGD_DEV')`), so
demo and ship builds contain none of it — verified: the demo screen has no DEV
badge, the DEV APK does. But the DEV APK exists in `dist/` next to the demo,
same size and date as `shipcfg`, and its "Win — 3 stars" goes through the
real `_onEnd` and posts `recordMini('coin_quest', right: 3)`.

Reproduced both sides of the floor: **level 1, DEV win after 38 s → 80 XP
paid** (server row `right 3, xp_gained 80`); **level 2, DEV win 4 s after
Play → refused `too_fast`, round left unclaimed, XP unchanged.** So the
server bounds it to one paid round per 15 s and 10 per day — the honest rate,
minted with a tap. The artefact should not sit in a folder that is handed to
testers, and DEV builds should compile in a dev-only `ARCADE_API`.

### A5. LOW — the client keeps a win the server refused
`app/lib/match3/ui/match3_screen.dart:80`, `app/lib/match3/progress.dart`

After the refused level 2 win above, the home screen shows **"6/180 stars"
against 80 XP**: stars and unlocks are local and persisted before the claim is
answered, and `recordMini` swallows `too_fast` as `(0, [])`. An honest player
who genuinely clears a vault in under 15 s loses the XP with no message; a
tester sees stars that XP contradicts. Fix shape: surface the refusal, or
hold the local record until the server answers.

### A6. LOW — `relbuild.cmd` ships pointed at localhost; log files collide
`relbuild.cmd:5`, `devbuild.cmd:8`, `demobuild.cmd:27`, `sideloadbuild.cmd:18`

A plain `relbuild.cmd` sets no `ARCADE_API`, so its "release" is the full app
talking to `http://localhost:8787`. `devbuild` and `relbuild` both truncate
`rel.log`; `demobuild` and `sideloadbuild` both truncate `demo.log` — the 16
Sept Process item, still open. Note also that `demobuild.cmd` builds the
**full** app (no `DGD_DEMO`) as an `.aab` with a real `ARCADE_API`; only
`sideloadbuild.cmd` builds the demo. Two scripts called "demo" build
different products.

### A7. INFORMATIONAL — identity churn on any 401
`app/lib/arcade/api.dart:141-145` · Flutter test "a 401 from any endpoint drops the identity"

A server reset, a proxy misconfiguration, or a hostile answer on a cleartext
dev URL costs the player their XP history and adds a ghost row to the board,
silently. A non-JSON 401 body, by contrast, is reported as offline and keeps
the token, because `_decode` parses before it looks at the status.

### A8. MEDIUM — the remote kill switch is specified and not implemented
`DGD-App-Integration-Brief.md §5` vs `app/lib/`

`arcade.enabled` and `arcade.rewards_enabled` are the Brief's answer to a
store reviewer objecting to the tab inside a trading app. Nothing in the client
reads any remote flag; `DGD_DEMO` and `DGD_APP_TAB` are compile-time. Until a
flag exists, the only way to turn rewards off is a new build through the
host's release train, which is the scenario the flags were meant to avoid.

### Verified sound on the emulator
- **The cache is display-only.** Inflated `ar.snapshot` XP to 999,999 and
  level to 99 on the device; on relaunch the home screen showed **80 XP**, the
  server row was untouched, and the on-disk snapshot had been rewritten to 80.
  Also pinned by the Flutter test "the local cache paints first and is then
  overwritten by the server; it is never sent", which asserts the claim body
  is exactly `{token, right, total, extra}`.
- Manifest surface is minimal: `INTERNET` only, one exported activity with the
  LAUNCHER filter, no deep links, no custom schemes.
  `network_security_config.xml` permits cleartext only to `localhost`,
  `127.0.0.1`, `10.0.2.2`.
- Coin Quest opens a server round the moment Play is pressed, before the
  tutorial is dismissed, so the duration floor measures real elapsed time.
- No answer key reaches the client on the tablet path (server test).

## iOS — static review here; checklist for the Mac

### I1. MEDIUM — no App Transport Security configuration at all
`app/ios/Runner/Info.plist`

No `NSAppTransportSecurity` key, so ATS is fully on and the compiled-in
`http://localhost:8787` is blocked. A DEV build on an iPhone therefore reads
"offline" with no other symptom — the iOS counterpart of Android's network
security config does not exist. When one is added it must be
`NSAllowsLocalNetworking` or a named exception domain, never
`NSAllowsArbitraryLoads`.

### I2. MEDIUM — the token lives in `NSUserDefaults`, unencrypted, in backups
`shared_preferences` on iOS

Same finding as A2. The Keychain is the platform answer.

### I3. INFORMATIONAL — stock project, no team, correct demo scripts
`Runner.xcodeproj`, `dist/mac-setup.sh`, `dist/mac-demobuild.sh`

Bundle id `co.digitalgold.arcade`, automatic signing, no `DEVELOPMENT_TEAM`
committed (the setup script tells the operator to add one). No URL schemes, no
usage strings. `mac-demobuild.sh` builds with `DGD_DEMO=true` only — the right
config, which means **A1 applies to it too**: a demo on a simulator will try
to register if it can reach a backend.

### For the Mac operator (`dist/mac-setup.sh`, then:)
1. `bash mac-demobuild.sh` on a booted simulator. With a local server running
   on the Mac and reachable at the compiled-in URL, watch for `POST
   /v1/players` — A1 says you will see one. Record it.
2. DEV build against the local server:
   `flutter run --dart-define=DGD_DEV=true --dart-define=ARCADE_API=http://<mac-ip>:8787`.
   Confirm ATS blocks plain http (I1) and that the app reports offline rather
   than crashing. Then repeat over https (or a scoped local-networking
   exception) and re-run the Android dynamic checks: one honest expedition,
   the DEV win on both sides of the 15 s floor, the cache-tamper relaunch.
3. Audio, the silent switch and haptics are only trustworthy on a real device,
   as the script itself says.

## How to re-run
```
cd arcade/server && npm ci && npm test
cd arcade/app && flutter test --dart-define=ARCADE_API=http://127.0.0.1:8799
```

which point that case reports as a passing todo and its flag should be removed.
