## RC1. HIGH — the embedded arcade trusts whatever is listening on localhost — FIXED same day (v1.0.2)

**What the binary does.** `ArcadeApi.base` falls back to
`http://localhost:8787` when `ARCADE_API` is not set (`api.dart:21-25`), and
`INTEGRATION.md` records that the AAR is built without it. The string is
compiled into `libapp.so`. The host's `Arcade` object pre-warms the Flutter
engine at ticker launch (`FlutterEngineCache`, `preWarm`, `executeDartEntrypoint`
in the host dex), so `main()` runs and `ArcadeProgress.load()` fires before
the user has touched anything.

**Reproduced, twice, from zero state** (wiped emulator, then wiped Pixel):

```
17:50:58 POST /v1/players  auth=-                                   body={"deviceHint":"android"}
17:50:58 GET  /v1/me       auth=Bearer IMPOSTOR-TOKEN-FROM-LOCALHOST
```

Both requests arrived at ticker launch with the arcade never opened. The
impostor answered the first with `{"token":"IMPOSTOR-TOKEN-FROM-LOCALHOST",
"playerId":"impostor-player"}`; the app stored it and sent it back as a bearer
on the very next call. At rest, `run-as` shows it in plaintext:

```
shared_prefs/FlutterSharedPreferences.xml
  flutter.api.token  = IMPOSTOR-TOKEN-FROM-LOCALHOST
  flutter.api.player = impostor-player
```

Opening the arcade then rendered normally with the OFFLINE chip (the impostor
503s everything else) — `redteam-runs/20260920T225000Z-rc-07aabe7/`.

**Why it matters.** On Android any installed app can bind `127.0.0.1:8787`
without a permission. Whoever does becomes this user's arcade backend: it
issues the identity, receives every subsequent request, and serves whatever
"weekly standings" and XP it likes. `usesCleartextTraffic="false"` did not
stop it — Flutter's `dart:io` permits cleartext to localhost regardless of
the manifest. The one mitigation in the code is real but narrow: a later 401
from a *real* backend clears the stored token (`api.dart:171-174`), so the
poisoned identity does not survive a correctly configured build.

This also re-opens the class of finding closed on 18 Sept as A1 (demo phones
home on cold start): the embed is neither a `DGD_DEMO` build, which makes
zero requests, nor a configured one. It is a dev-shaped build in a release
candidate.

**Fix, in order of preference.**
1. `ArcadeApi`: in a non-debug build with no `ARCADE_API`, there is **no
   backend** — behave as the demo does and never fall back to localhost. The
   localhost default is right for `flutter run`; it is wrong compiled into
   anything that leaves the machine.
2. `build_aar.cmd`: refuse to build unless `ARCADE_API` or `DGD_DEMO=true` is
   passed, the same way it already refuses without JDK 21.
3. Until a backend is hosted, build the embed with `DGD_DEMO=true`.
4. Regression: a `HOLDS` case in `arcade_api_test.dart` that a build with
   `DGD_APP_TAB=true` and no `ARCADE_API` makes zero requests, mirroring the
   existing demo case.

## RC2. MEDIUM — the RC cannot be reproduced from any pinned commit

Policy §2.1 and §2.3 require a clean-room rebuild that matches the shipped
artefact. For this RC that is not possible:

- The native app plus every integration change (the `Arcade` entry point,
  the Gradle bumps, the `arcade-repo` Maven mirror) lives only in
  `C:\src\dgd-native`, which **has no git history**.
- The arcade module is generated from `C:\src\puzzle-app` at tag `v1.0.1`
  (`cebd068`). The repo mirror `arcade/v1/app` is still at `1.0.0+100` and
  lacks the `sheetMargin` fix, so the source of the shipped arcade is not in
  this repository either.
- The AAR is a binary checked in "beside" the native app, outside this repo.

None of this is a defect in the build. It is the situation the 18 Sept
audit's Process section predicted ("a mirror that is copied by hand will
drift again"), and it means the ship gate in §4 fails by definition until the
native tree is under version control and the mirror is re-synced from
`v1.0.1`. Until then the artefact is trusted on the builder's word.

## RC3. LOW — the artefact says 1.0.1, the manifest says 1.0.0 (1)

`versionName='1.0.0' versionCode='1'`, identical to the pre-merge ticker. The
arcade module inside carries `1.0.1+101`, but the host — the thing Play and
the OS version — has not moved. Two consequences: `pm dumpsys` cannot tell
this build from the ticker-fix build on a device, and a Play update from any
earlier upload will be refused until `versionCode` increases.

## RC4. LOW — 32-bit x86 is declared with no engine behind it

`native-code: 'arm64-v8a' 'armeabi-v7a' 'x86' 'x86_64'`, but `lib/x86/` holds
only `libandroidx.graphics.path.so`, `libdartjni.so` and
`libdatastore_shared_counter.so` — no `libflutter.so`, no `libapp.so`. On a
32-bit x86 device the ticker installs and runs and the arcade tap throws
`UnsatisfiedLinkError`. Such devices are close to extinct and an App Bundle
splits by ABI, so this is a tidy-up: add `abiFilters` without `x86`, or
accept it and say so.

## RC5. INFO — `DGD_APP_TAB` suppression is still unverified, and the string test is inconclusive

`INTEGRATION.md` is right that only a won level proves it. I tried the cheap
static check: the winner voice-line asset names (`vo_you_win.wav`,
`vo_level_complete.wav`) are present in `libapp.so`. That does **not** show
the flag is off — a `const` list survives tree-shaking even when its only
caller is dead code — so it proves nothing either way. Two ways to make this
checkable without a human playing sixty levels: build the AAR once with
`DGD_DEV=true` for a verification pass, or have `inAppTab` also drive
something visible at launch (a line in "Settings and your data").

## RC6. INFO — debug-build properties, unchanged from the ticker-fix audit

`debuggable=true`, debug certificate, Compose `PreviewActivity` exported,
`allowBackup=true`. The arcade's plaintext token now sits under the host's
backup flag; the standalone v1 manifest never set `allowBackup` either, so
this is not merge-introduced, but the host's backup rules now govern both
halves and N4 in the ticker-fix audit applies to the arcade's `api.token` as
well.

## RC7. INFO — the emulator, not the app

With the emulator's default software GPU, tapping the arcade **segfaulted the
emulator host process** (exit 139) twice at the same instant — Impeller's
Vulkan backend on SwiftShader. `-feature -Vulkan` makes Flutter fall back to
OpenGLES and everything works. Anyone reproducing on an AVD will hit this;
it is in the re-run block below.

## How to re-run
```
# static
arcade/tools/redteam.sh --ref HEAD --mirror none --apk arcade/integration/DGD-merged-arcade-v1.0.1-debug.apk

# dynamic, clean emulator (Vulkan off: the software GPU segfaults on Impeller's Vulkan path)
emulator -avd dgd_api35 -wipe-data -no-snapshot -no-window -gpu swiftshader_indirect -feature -Vulkan
adb -e shell "svc wifi disable; svc data disable"
python impostor.py 18788 impostor.log          # answers POST /v1/players with a token, 503 otherwise
adb -e reverse tcp:8787 tcp:18788
adb -e install arcade/integration/DGD-merged-arcade-v1.0.1-debug.apk
adb -e shell am start -n com.digitalgold.ticker/.MainActivity
sleep 10; cat impostor.log                     # two requests, arcade never opened
adb -e shell run-as com.digitalgold.ticker cat shared_prefs/FlutterSharedPreferences.xml
```
